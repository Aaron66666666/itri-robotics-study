# 三代理（Tracker／Predictor／Commander）結果

2026-11-27 晚間完成。規劃見 `docs/plan_three_agents.md`。兩個版本都和現有版本跑同樣的測試；結果（包括沒達標的地方）照實記錄。

## 一、TM5S 取放三代理

### 結果

| 測試 | 單一 Agent | 三代理 |
|---|---|---|
| 假桌面，12 句 × 2 輪（Llama 3.1 8B） | 16/24 | **24/24** |
| Gazebo 實機，12 句（相機 + YOLO v4 + 真的夾取） | 8/12 | **12/12** |
| 平均工具呼叫次數（Gazebo） | 2.1 | 3.2 |
| 平均每句時間（Gazebo，含手臂動作） | 26 秒 | 36 秒 |
| 最後回報被事實檢查改寫的次數 | — | 0/36 |

單一 Agent 做不到、三代理做得到的指令：

| 指令 | 情境 | 單一 Agent | 三代理 |
|---|---|---|---|
| 把瓶子放到右邊 | 右邊被杯子占住 | 只能回報被占用 | 先把杯子移到 Predictor 建議的空位，再放瓶子 |
| 把杯子放到右邊，再把瓶子放到中間 | 右邊被瓶子占住 | 杯子失敗 | 先把瓶子移到中間（它本來就要去的地方），再放杯子 |
| 把杯子和瓶子都放到中間 | 只放得下一個 | 回答不清楚 | 放一個，另一個回報沒有空間 |
| 把杯子放到左邊（杯子在 0.86 m 外） | 搆不到 | 回答不正確 | 動手前就由 Predictor 判定搆不到，不嘗試 |

原始結果：`ai-agent/eval_results/team_fake_llama_*.json`、`team_gazebo_llama_*.json`（每一句都含完整的訊息板紀錄）。

### 第一版失敗，以及怎麼修好

第一版三代理反而比單一 Agent 差（假桌面 8/24、Gazebo 4/12）。逐一看訊息板紀錄後找到原因並修正：

| 問題 | 原因 | 修正 | 效果 |
|---|---|---|---|
| 一直說「桌上沒有東西」 | Commander（Llama）跳過觀察就直接預測 | Predictor 發現沒看過桌面時自己先觀察 | 8/24 → 20/24 |
| 沒預測就移動被擋，之後就放棄 | 小模型不照流程 | `move_object` 沒有最新預測時自己請 Predictor 判斷；不可行就回傳原因（安全性不變：每次移動仍由 Predictor 判定） | — |
| 區域名稱變成亂碼（`Ա體山`） | 中文區域名稱讓模型輸出亂碼 | 工具接受中文別名、拒絕訊息只用英文 | 亂碼消失 |
| 清出空位後忘了原本的動作 | 小模型記不住整個計畫 | 解析使用者的「物體 → 區域」；擋路的物體優先移到它本來就要去的地方；Commander 停下時若還有現在可行的要求，交回給它繼續（最多 3 輪） | 22/24 → 24/24 |
| 回報宣稱成功或編造座標 | 模型編造 | 程式檢查回報：宣稱移動卻沒有成功紀錄、出現工具結果裡沒有的數字、提到工具名稱 → 改用由訊息板產生的事實報告 | 最終 0 次需要改寫 |
| Gazebo 評估中途當掉 | 讀 Gazebo 真實位置偶爾少了一個物體 | 重試讀取；每句結果立即存檔 | — |

設計重點：**語言模型只負責理解和決策，追蹤、預測、安全規則和事實檢查都是程式**，所以小模型出錯時不會造成錯誤的動作或錯誤的回報。

## 二、自走車三代理

### 架構

Tracker（人物軌跡 + 距離方位估計）→ Predictor（卡爾曼濾波預測 3 秒內會不會進入車子前方通道）→ Commander（正常／減速／停車，停車後要連續 1 秒「無風險」才恢復；預測過期就停車）。原本驗收過的控制器沒有改，只是不再自己處理行人，輸出改經 Commander。

人物距離用 Gazebo 真實位置校正：`RANGE_K = 989.1`（距離 = 989.1 ÷ 偵測框高度像素）。

### 場景結果（各 2 次，到達時間取平均，距離取最小）

| 場景 | 到達杯子（原 → 三代理） | 停車時間 | 移動中和人的最小距離（原 → 三代理） |
|---|---|---|---|
| S1 人橫越車子前方 | 21.0 → 23.6 秒 | 7.0 → 9.5 秒 | 0.37 → **0.42 m** |
| S2 人在旁邊平行走過 | 25.9 → **23.3 秒** | 11.9 → **8.5 秒** | 0.65 → 0.65 m |
| S3 人站在路邊（看得到，不擋路） | **80 秒內沒到達** → **18.2 秒** | 86 → **4 秒** | — → 2.01 m |
| S4 人迎面走進路線再離開 | 35.8 → **32.8 秒** | 21.8 → **18.6 秒** | 0.94 → **0.80 m** |
| S5 原本的人員停止驗收 | 26.4 → 25.5 秒 | 12.4 → 11.1 秒 | 2.27 → 2.23 m |

全部 20 次都沒有碰撞。原始資料：`projects/diff_drive_yolo/docs/evidence/2026-11-27_team/`（真實位置 CSV、launch log、每次的指標）。

### 結論

- **效率：** 人看得到但不擋路時，三代理明顯較好。S3 原控制器一直停著到不了杯子，三代理 18 秒到達；S2、S4 也較快。
- **安全：** 沒有碰撞；S1、S2、S5 和原控制器相同或更好。**S4 沒達到規劃中「不比原控制器更接近行人」的標準**：移動中最小距離 0.80 m，原控制器 0.94 m（原控制器只要看得到人就完全不動，所以一定最保守）。
- **改善過程：** 第一版三代理在 S4 移動中只有 0.60–0.63 m，原因是人剛離開路線時就以半速恢復。加上「停車後連續 1 秒無風險才恢復」後提高到 0.80–0.92 m。另外試過「人在 1 m 內就停」的保守模式（`stop_radius`），幾乎沒有效果，因為人走到車子旁邊時已經在相機視野（±30°）外，看不到。
- **限制：** 只有一台朝前的相機，車子側面是盲區；實際部署應該加上側面感測（光達或更廣角的相機），而不是只靠調參數。

## 三、YOLO v5（乾淨資料重新訓練）

階段 2 的合成資料影像上都有 Gazebo 畫上去的綠框。用一般相機的影像重新產生同樣的 2800 張資料，以和 v3 相同的方法重新訓練成 v5：

| 項目 | v3 | v5 |
|---|---|---|
| 乾淨測試集 mAP50 | 0.884 | **0.988** |
| 杯子 | 0.717 | **0.985** |
| 自走車相機最弱的杯子影格 | 0.761 | **0.852** |
| 自走車閉環回歸（杯子、目標遺失、人員停止、原瓶子場景） | 通過 | **通過**，停止位置差 ≤ 3 cm |

v5 每一項都相同或更好。

### v3、v5 兩個都保留（2026-11-27 晚）

使用者決定兩個模型都留著：新增 `yolo_model:=v3|v5|coco` 參數，一個字切換；`model_path:=檔案` 仍可指定其他權重。預設仍是 v3。

- **切換確認：** 實際啟動 launch，預設載入 v3、`yolo_model:=v5` 載入 v5、`coco` 載入原模型、三代理 launch 也會帶到；名稱打錯（例如 `v4`）時 launch 直接報錯並列出可用名稱。
- **預設行為不變：** 改完後用預設參數重跑 F1–F4，全部通過，停止位置 0.534／0.704／0.529／0.973 m，和 2026-11-24 驗收時相差不到 3 cm。
- **人物距離校正：** v5 的 `RANGE_K` 為 993.6，v3 為 989.1，差 0.5%，所以共用同一個值。

用 v5 重跑 S1–S5（原控制器、三代理各 2 次），和 v3 的結果並排：

| 場景 | 到達時間：原控制器 v3 → v5 | 到達時間：三代理 v3 → v5 | 移動中最小距離：原控制器 v3 → v5 | 移動中最小距離：三代理 v3 → v5 |
|---|---|---|---|---|
| S1 橫越 | 21.0 → 20.9 秒 | 23.6 → **20.8 秒** | 0.37 → 0.42 m | 0.42 → **0.47 m** |
| S2 平行 | 25.9 → 24.4 秒 | 23.3 → **20.2 秒** | 0.65 → 0.65 m | 0.65 → 0.65 m |
| S3 站在路邊 | 沒到達 → 沒到達 | 18.2 → 18.0 秒 | — | 2.01 → 2.01 m |
| S4 迎面 | 35.8 → 34.9 秒 | 32.8 → **29.3 秒** | 0.94 → 1.05 m | 0.80 → 0.79 m |
| S5 原驗收 | 26.4 → 22.9 秒 | 25.5 → 24.6 秒 | 2.27 → 2.21 m | 2.23 → 2.24 m |

- 40 次（v3、v5 各 20 次）都沒有碰撞。
- 換成 v5 後兩種控制器都變快或持平。三代理在 S1、S2、S4 快 3–4 秒。原因是 v5 較少暫時看丟杯子：控制器因為看丟杯子而暫停（`target_lost_wait`）的次數，三代理從 19 次降到 2 次，原控制器從 9 次降到 0 次（各 10 次執行的合計）。
- S4 的問題不會因為換模型消失：三代理移動中仍只有 0.79 m（原控制器 1.05 m），原因是相機看不到車子側面，和 YOLO 模型無關。改善方法見下一節（光達）。
