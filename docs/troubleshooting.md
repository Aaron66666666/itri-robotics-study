# 問題與排除紀錄

整理各階段實際遇到的問題、找出原因的方法，以及最後怎麼解決和驗證。

## 排除問題的方法

每個問題都照同樣的流程處理：

1. **重現**：先找到能穩定重現問題的最小情境，例如只啟動一個節點，或固定同一個場景。
2. **量測，不靠猜**：用 odometry、Gazebo 實際位置、log、TensorBoard 數值確認問題真的存在，以及出在哪一層。
3. **找根本原因**：一次只改一個變數，確認改了之後問題消失，改回去問題又出現。
4. **加回歸測試**：能寫成自動測試的就寫，避免同樣的問題再發生。
5. **重跑驗收**：修完重跑相關的驗收，留下 log 作為證據。

## 1. 自走車 + YOLO 自主控制

| 問題 | 原因 | 排除方式 | 驗證 |
|---|---|---|---|
| YOLO 的信心門檻設定會改掉控制器的停止門檻 | 兩個 Launch 檔的參數名稱相同，被引入（include）的 Launch 參數會外洩到上層 | 用 `GroupAction(scoped=True)` 隔離相機 Launch 的參數 | 兩個門檻可以獨立設定，自動測試通過 |
| 改用 GPU（`device:=0`）後相機節點直接當掉 | ROS 2 把 `0` 自動解析成整數，但節點宣告的參數是字串 | 在 Launch 用 `ParameterValue(..., value_type=str)` 強制轉成字串 | GPU 版人物情境測試通過 |
| 人離開畫面後，車輛不再接近目標 | 「已鎖定目標」的狀態在人出現時被清掉，人離開後沒有恢復 | 調整狀態機的鎖定邏輯，等待期間保留目標鎖定 | 新增單元測試；人物端到端測試連續 2 次通過 |
| 目標框閃爍時重複觸發停止動作 | 偵測一下有一下沒有，每次重新出現都被當成新目標 | 加入目標遺失逾時（`target_loss_timeout`），短暫漏檢不算遺失 | 漏檢驗收項目通過 |
| 圓柱瓶子只在起點被辨識，車一前進就辨識不到 | 原始 YOLO 把瓶子判成杯子（0.45），距離一變就掉到 0.13 | 先換成辨識穩定的白色馬克杯場景完成驗收；之後在階段 2 用自訂資料訓練徹底解決 | 新模型瓶子分數 0.00 → 0.93 |
| 驗收腳本把自己的終端機也關掉（exit 144） | 用 `pkill -f` 比對程序名稱時，比對字串也出現在自己的指令列裡 | 改用 `[x]` 形式的比對字串，或用程序 ID 停止 | 腳本可以重複執行 |

## 2. UR5e 機械手臂取放

| 問題 | 原因 | 排除方式 | 驗證 |
|---|---|---|---|
| 右夾指在 Gazebo 裡完全不動 | 夾指的起始位置剛好在關節極限邊界，被 DART 物理引擎卡住 | 兩指的關節極限各留 2 mm 餘量 | 夾爪監看腳本確認兩指都會動 |
| MoveIt 找不到逆運動學解（`NO_IK_SOLUTION`） | 手臂裝在地面，桌面高 0.70 m，由上往下夾取超出 UR5e 的可達範圍 | 手臂改裝在 0.70 m 高的底座上 | 關節誤差 ≤ 0.005 rad，末端誤差約 1 mm |
| 換方向搬運時，直線路徑規劃失敗 | 目標姿態沒有限制繞垂直軸的旋轉，手腕會轉到奇怪的角度 | 目標姿態的旋轉容許誤差設為 0.05 rad | 反方向搬運從失敗變成成功（失敗前後的 log 都有保存） |
| URDF 讀取失敗 | URDF 註解裡的「: 」被 YAML 解析器誤判 | 移除註解中的冒號 | `check_urdf` 通過 |

**方塊位置誤差的單位是 mm（公釐），不是 cm。** 這是用 Gazebo 讀出方塊放下後的實際座標，和目標位置相比：例如目標 (0.55, 0.30)，實測 (0.5502, 0.2988)，y 方向差 1.2 mm。2026-11-25 錄影時連續 3 次的誤差是 0.1–1.5 mm（`projects/ur5e_gazebo_pick_place/docs/evidence_2026-11-25_gui_video/results.csv`），所以整體寫成「2 mm 以內」比較準確。

## 2b. 達明 TM5S-900（Gazebo + MoveIt 2）

| 問題 | 原因 | 排除方式 | 驗證 |
|---|---|---|---|
| 官方 Gazebo 外掛在 Jazzy 不存在 | 達明官方套件是 ROS 2 Humble 版，用 `ign_ros2_control` | 自己寫 URDF，改用 Jazzy 的 `gz_ros2_control` | 三個控制器全部 active |
| 官方 Gazebo 巨集是舊版 Gazebo Classic 的 | `macro.gazebo.xacro` 用 `libgazebo_ros_control.so` | 只引用官方的運動學、網格和慣量巨集 | URDF 檢查通過，Gazebo 正常產生手臂 |
| MoveIt 規劃後無法加上時間參數 | 官方關節限制沒有開加速度限制 | 自己的 `joint_limits.yaml` 補上加速度限制 | 關節、末端、取放三個階段都成功 |
| 官方 MoveIt 設定的連桿名稱對不上 | 官方 MoveIt 用 `link_0`／`base`，Gazebo 版模型的 root 是 `base_link` | SRDF 改成 `base_link` → `flange` | 末端誤差約 2 mm，取放 3/3 |
| 預備姿態要讓夾爪朝下、位在桌子上方 | 不同手臂的關節定義不同，UR5e 的姿態不能直接用 | 先用正向運動學算出 (0, 0, 90°, 0, 90°, 0) 時法蘭朝下，再轉第 1 軸對準桌子 | 法蘭在 (0.37, 0.39, 1.14)，朝下 |

## 2c. TM5S 視覺引導取放（2026-11-27）

| 問題 | 原因 | 排除方式 | 驗證 |
|---|---|---|---|
| 驗證集 mAP 0.995，實際卻有 3/20 個杯子認不出來 | **訓練影像上有綠色框**：Gazebo 的 bounding box camera 輸出的影像會把標註框畫上去，模型學到「找綠框」 | 把不同位置的失敗畫面和訓練影像並排比對才發現；改用同位置一般相機的影像，只取 bounding box camera 的標註，依時間戳配對 | 20/20 偵測，最低信心值 0.94 |
| 杯子分數很低（0.12） | 把手正對相機，看起來只是圓柱 | 測試 6 個角度，選 -45°（0.75）且不會卡到手指 | 偵測正常 |
| 瓶子夾不起來 | 手指只伸出夾爪本體下方 8.5 cm，23 cm 的瓶子夾瓶身時本體會撞到瓶頸 | 瓶子改 16 cm，夾取高度依物體高度計算 | 取放成功 |
| 取放程式卡住不動 | `joint_state_broadcaster` 啟動時切換逾時（5 秒），沒有關節狀態，程式無限等待 | 切換逾時改 30 秒、啟動後檢查並重試、程式等待上限 30 秒 | 之後 20 次取放都正常 |
| 1/10 取放失敗 | 物體離底座 0.865 m，超出 TM5S 從上往下夾的工作範圍（IK 無解） | 擺放和放置限制在 0.80 m 內 | 10/10 |

## 3. 階段 1：AI Agent（本機 Ollama）

| 問題 | 原因 | 排除方式 | 驗證 |
|---|---|---|---|
| WSL 連不到 Windows 上的 Ollama | WSL 是 NAT 網路，`localhost` 指不到 Windows；Windows 防火牆也擋住連線 | Ollama 改成監聽所有介面，防火牆只開放 WSL 網段；Agent 自動偵測 Windows 主機 IP | 從 WSL 呼叫成功，約 0.6–1 秒回應 |
| 防火牆設定後仍然連不上 | 第一次跳出的存取視窗按了「取消」，Windows 自動建立封鎖規則，優先權比允許規則高 | 找出並刪除 Ollama 的封鎖規則 | 重新連線成功 |
| 模型編造測試結果 | 小模型沒拿到工具結果也會「回答」 | 提示詞規定只能引用工具結果；Multi-Agent 的審查者用程式核對數字 | 審查正確率 14/16，0 次錯誤核准 |
| 模型自己跑使用者沒要求的測試 | 模型「好心」多做 | 在程式層加入規則，只允許使用者點名的情境 | 評估中的禁止動作檢查全部通過 |
| 回答混用簡體字 | Qwen 模型的訓練資料偏簡體 | 加強提示詞，預設模型改為 Llama 3.1 8B | 繁體中文檢查通過 |
| 審查者誤判 | 一次判斷整份報告太難，小模型會漏看 | 改成先把要求拆成項目，再逐項判斷 | 正確率從 8/16、12/16 提升到 14/16 |
