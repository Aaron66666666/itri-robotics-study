# 規劃：Tracker／Predictor／Commander 三代理（TM5S 取放 + 自走車）

2026-11-27 擬定。起因：使用者在 IG 看到一段提示詞，要求「三個專職 agent（Tracker、Predictor、Commander）互相溝通、共用工具、自己解決問題」的 Python 樣板。這裡不做只有架構的樣板，而是直接套用到已經驗收過的兩個系統上，每一部分都要有測試、有量化評估、能和現有版本比較。

## 共同原則（「扎實」的定義）

1. **每個 agent 都有明確、可測的責任**，不是三個互相聊天的語言模型。
2. **能用程式做好的就用程式**（追蹤、預測、安全規則），語言模型只負責需要理解語言和規劃的部分。理由：語言模型每次回應要 0.6–1 秒、偶爾會出錯；即時控制和安全判斷不能依賴它。
3. **溝通看得到**：所有 agent 之間的訊息都寫進共用的訊息板，每一次決策都附上理由，事後可以完整重播。
4. **安全規則寫在程式裡**，不只寫在提示詞裡（沿用階段 1 的做法）。
5. **和現有版本比較**：三代理一定要和現在的單一 Agent／現在的控制器跑同樣的測試，用數字說明好在哪裡、代價是什麼。
6. **先用假資料測試，再用 Gazebo 驗收**；結果（包括失敗）都記錄。

## 一、TM5S 取放三代理（非即時，語言模型適合）

### 角色

| Agent | 實作 | 工具（放在共用工具表） | 輸出 |
|---|---|---|---|
| **Tracker** | 程式 | `observe_table`：拍一張、更新每個物體的追蹤紀錄 | 每個物體的位置、信心值、這次和上次比移動了多少、位置是否穩定（連續兩次觀測相差 < 1 cm） |
| **Predictor** | 程式（規則 + 實測數據） | `predict_move(object, area)` | 可不可行、原因（搆不到／區域被占用／物體不穩定）、成功機率、預估時間、擋路的物體、建議的替代空位 |
| **Commander** | 本機 Llama 3.1 8B | 上面兩個工具 + `move_object(object, area)`、`report` | 理解中文指令、決定順序、必要時先清出空位、回報 |

Predictor 的成功率用實測數據估計：20 次視覺取放（工作範圍內 20/20、超出範圍 0/1），以 Laplace 平滑後給出機率；超出 0.80 m 一律判定不可行。預估時間用實測的每次約 25 秒。

### 溝通與安全

- 共用訊息板（`Blackboard`）：每則訊息記錄寄件者、收件者、類型、內容、時間；結束時可以輸出成完整的對話紀錄。
- 程式層規則：
  - `move_object` 只有在 Predictor 剛對**同一個物體、同一個區域、同一份桌面狀態**判定可行之後才能執行（桌面一有變化，之前的預測就失效）；
  - 只能移動使用者提到的物體；**唯一例外**是 Predictor 指出「目標區域被某物體擋住」時，Commander 可以把那個擋路的物體移到 Predictor 建議的空位；
  - 只能用定義好的四個區域。

### 評估（和單一 Agent 比較）

沿用 D 的 8 句指令，再加 4 句需要規劃或預測的：

| 指令 | 情境 | 期望 |
|---|---|---|
| 把瓶子放到右邊 | 右邊被杯子占住 | 三代理：先把杯子移到建議空位，再放瓶子（單一 Agent 只能回報被占用） |
| 把杯子放到左邊 | 杯子在 0.85 m 外，搆不到 | 不動手，回報搆不到（單一 Agent 會實際嘗試然後失敗） |
| 把杯子和瓶子都放到中間 | 同一區域放不下兩個 | 放一個，另一個回報沒有空間，不能硬放 |
| 把杯子放到右邊，瓶子不要動 | 右邊被瓶子占住 | 不能移動瓶子，回報無法完成 |

指標：成功率、是否有不該動的動作、工具呼叫數、花費時間、是否編造結果、繁體中文。先用假桌面（快、可重複多次），再用 Gazebo 驗收。

## 二、自走車三代理（即時，追蹤和預測必須是程式）

### 要解決的問題

現在的控制器規則是「畫面中只要看到人就停車」。很安全，但效率差：人站在路邊、走開或平行走過時也會停。三代理版本的目標是**該停的時候一樣停（甚至更早停），不需要停的時候不停**。

### 角色（三個 ROS 2 節點）

| Agent | 實作 | 輸入 → 輸出 |
|---|---|---|
| **Tracker** | ROS 2 節點 | `/yolo/detections` → `/team/tracks`：把每一幀的人連成軌跡（編號），用偵測框高度和相機參數估計人的距離與方位（人的身高用 Gazebo 真實位置校正） |
| **Predictor** | ROS 2 節點 | `/team/tracks` + 車速 → `/team/prediction`：每條軌跡用卡爾曼濾波估計速度，預測未來 3 秒的位置，判斷會不會進入車子前方的通道，算出碰撞時間（TTC）和風險等級 |
| **Commander** | ROS 2 節點 | 原控制器的速度命令 + `/team/prediction` → 最終的 `cmd_vel`：依風險決定正常、減速或停車，並記錄每次決策的理由 |

原本已驗收的控制器完全不改；Commander 只是夾在它和車子中間（新的 launch 檔做重新對應），隨時可以切回原版本。

**語言模型的角色：** 即時迴路不使用語言模型。另外提供一個可選的「任務指揮」功能：用中文設定任務參數（例如「找杯子，行人靠近 2 公尺內就停」），由語言模型轉成參數，經過程式檢查範圍後才套用。

### 評估場景（Gazebo，人物會移動）

| 場景 | 人的動作 | 原控制器預期 | 三代理預期 |
|---|---|---|---|
| S1 穿越 | 從側邊走進車子前方的路線 | 看到就停 | 提早預測、停車讓行，人離開後恢復 |
| S2 平行 | 在車子旁邊平行走，不進入路線 | 一直停（不必要） | 持續前進（可以減速） |
| S3 站在路邊 | 站在側邊不動 | 一直停（不必要） | 持續前進 |
| S4 迎面走來 | 從正前方朝車子走來 | 停 | 停，而且停得比較早或距離比較遠 |
| S5 回歸 | 原本的人員停止測試 | 通過 | 也要通過 |

指標：**安全**（和人的最小距離，必須都大於安全距離；碰撞次數 0）、**效率**（到達杯子的時間、不必要停車的時間）、**反應**（人進入路線到車子停下的時間）。每個場景至少跑 2 次。另外用錄好的軌跡對 Tracker 和 Predictor 做離線單元測試（距離估計誤差、預測誤差）。

## 三、順序與時間

| 項目 | 預估 | 需要 GPU |
|---|---|---|
| TM5S 三代理：程式 + 假桌面測試 | 2–3 小時 | 否（Ollama 評估時需要） |
| 自走車三代理：Tracker／Predictor／Commander 節點 + 離線測試 | 3–4 小時 | 否 |
| 完成目前排程：自走車 YOLO v5、回歸測試、D 的 Gazebo 驗收 | 約 1.5 小時 | 是 |
| TM5S 三代理 Gazebo 驗收（和單一 Agent 比較） | 約 1.5 小時 | 是 |
| 自走車移動人物場景 S1–S5（各 2 次，和原控制器比較） | 約 2 小時 | 是 |
| 文件、圖表、push | 1 小時 | 否 |

合計約 11–13 小時。GPU 一次只跑一件事（Ollama、YOLO 訓練、Gazebo 互相搶顯示記憶體）。

## 四、風險

| 風險 | 對策 |
|---|---|
| 單眼相機估計行人距離不準 | 用 Gazebo 真實位置校正身高參數；評估時記錄估計誤差；安全判斷留餘裕 |
| 卡爾曼預測在人剛出現時不穩 | 軌跡至少有 3 次觀測才預測，之前一律視為高風險（保守） |
| 三代理反而比原控制器危險 | S5 回歸 + 最小距離指標；任何場景只要比原控制器更接近行人就算失敗 |
| Commander（語言模型）規劃錯誤 | 程式層規則（只有 Predictor 判定可行的動作才能執行）；評估中記錄每次被擋下的動作 |
| GPU 記憶體不足 | 依序執行，不同時跑 |
